## Summary

The platform can now run paper trading continuously: it keeps its state across
restarts, authorises and records every operation, backs itself up and can be
restored, monitors itself and reports daily, and its results can be reproduced
from stored provenance. All of this was tested, including an end-to-end run of
the whole chain on the real Docker stack with signals generated by the strategy.

Two things were **not** done and are not claimed:

1. **The 7-day continuous paper-trading test has not been run.** It needs a
   machine that stays on for a week; the environment this work was done in does
   not. Everything to run it on a VPS is in place and described in the
   [runbook](paper-trading-runbook.md). `qts report soak` returns `IN PROGRESS`
   until seven days of monitoring are recorded.
2. **The strategy is not statistically validated** — the new studies confirm it
   rather than fix it (see [Quantitative validation](#phase-4--quantitative-validation)).

## Phase 1 — risk engine and Freqtrade

One model for every order ([risk.md](risk.md#authorisation-model)):

- **New exposure fails closed**: any rejection, doubt or internal error means no entry.
- **Reductions go through a reduce-only path** that looks only at the order and
  the position it closes. Nothing that blocks an entry can block an exit. Before
  this change a non-finite cash figure, or a symbol removed from the whitelist,
  rejected the exit as well.
- An exit cannot exceed the position, carry the entry reason or contain nonsense numbers.

| Case | Implemented | Test |
|---|---|---|
| Stop loss | platform session; Freqtrade stop fixed at the entry fill and stored with the trade | closes with the kill switch active; stored stop identical after a bot restart with the entry candle gone from memory |
| Take profit | order reason and mapping of Freqtrade ROI exits; the strategy itself has no profit target | partial exit with the take-profit reason |
| Trailing stop | reported as `trailing_stop`; highest level persisted | reason and price; identical with a restart after every candle |
| Partial close | `qts paper close --fraction`; Freqtrade partials journaled on fill | remainder keeps its stop; quantities and P&L |
| Emergency close | `--all --emergency`; `flatten_on_kill_switch` in both engines | positions closed, later entries vetoed |
| Manual close | `qts paper close`; Freqtrade force-exit journaled as `manual` | executes at the next open with the kill switch on |
| Exchange errors | step abandoned, last committed state kept, failure counted; Freqtrade entries fail closed, exits fail open | no trace of the failed step, retry books each order once; three failures trip the kill switch |
| Restart with an open position | state from the database; Freqtrade stop from its own database | same exits with and without restarts |

Kill switch with Freqtrade already running, verified live in Docker: after
`risk kill` from another container the bot refused the next entry without a
restart, and still executed a partial and a full exit; entry, veto and exit
appear in `risk_decisions` of the platform database. Freqtrade's own backtest of
the adapter is unchanged (29 trades, +79.78 %).

Restore, verified three ways:

1. `scripts/restore_test.sh` (non-destructive, in CI): every table identical by
   row count and checksum; roles restored unprivileged; schema revision; state archive.
2. Simulated data loss on a running stack — fills, equity and paper state
   deleted, the `trades` table dropped, kill switch cleared — then
   `scripts/restore.sh`: identical fingerprint, kill switch active again with its
   original reason, trading resumed.
3. In the end-to-end test: **every volume destroyed**, restore, trading continued
   and still equal to the backtest.

Recovered and checked: positions, orders (risk decisions), fills, trades,
portfolio state (cash, pending orders), risk limits (equity peak, daily halt,
error count), kill-switch state.

An existing installation is upgraded in place: verified on a volume created by

parameter combinations without a multiple-testing correction, daily candles,
simulated fills. Nothing was optimised after the fact.

## Phase 5 — end-to-end paper trading

`scripts/e2e_paper_test.sh`: market data → strategy → signal → risk engine →
execution → PostgreSQL → Grafana, on the real Docker stack, with the operator's
own CLI commands, one candle at a time. **No entry is forced**: the strategy
produces the signals on a deterministic synthetic market.

Passed locally (3 min 10 s; 9 fills, 557 signal rows, 33 orders evaluated, 279
candles): entries from strategy signals → positions and stops intact after a
PostgreSQL restart and after all containers were destroyed → duplicated candles
→ a candle that never arrives → data three days late → stop loss and exit signal
→ **session equal to an independent backtest to 12 digits** → fills visible
through Grafana → backup, all volumes destroyed, restore, trading continues →
kill switch refusing the entries the strategy asks for → partial manual close →
soak test not declared passed.

The market in this test is synthetic by design (it must contain every event and
be the same on every run). The same chain on real market data is what the
continuous run is for.

## Phase 6 — resilience

| Scenario | How it was tested | Outcome |
|---|---|---|
| Docker restart | end-to-end: all containers destroyed and recreated; earlier: daemon restart | state intact |
| PostgreSQL restart | end-to-end, with positions open | positions and stops intact |
| Temporary loss of data / late data | pytest + end-to-end | error recorded, nothing traded on stale data, backlog processed once |
| Connection interrupted | pytest: source failing, real source with network and HTTP errors | counted; resumes; below three failures no kill switch |
| Duplicated candles | pytest + end-to-end | no new fill, no new candle |
| Missing candles | pytest + end-to-end | skipped, never invented |
| Exchange errors | pytest: broker rejecting mid-step; Freqtrade adapter | no trace of the failed step; each order booked once |
| Restart during an open position | pytest (every candle in a new process) + end-to-end | same stop, same exits |
| Interruption while recording an order | pytest: connection lost at each of the nine writes of a step | nothing left behind; retry equals the undisturbed session |

In every case: no duplicated order and no exposure without a risk approval,
asserted against an independent backtest.
